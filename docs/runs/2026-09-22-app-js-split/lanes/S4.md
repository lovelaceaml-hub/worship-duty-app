**The central problem this section had to solve**: `render` and other
appearance-dispatch functions were already known (from Section 3) to be
monkey-patched by `design-gallery/host-bridge.js`, spliced as literal text
right before `app.js`'s closing `init();` call. A full sweep of all 8 gallery
source files `design-gallery/build.mjs` splices into the built `app.js`
(not just `host-bridge.js`) found the real patched set is **14 names**:
`host-bridge.js`'s 11 (`render`, `renderSchedule`, `renderMy`, `renderManage`,
`renderManageServices`, `renderManagePlanning`, `renderManageRequests`,
`renderManagePeople`, `renderFeatures`, `renderManageData`, `renderSiteLock`)
plus 3 more discovered by the sweep, each reassigned by a different Prism/
Aurora prototype source: `renderUnlock`/`renderCreatePin`
(`prototype-prism/all-pages.js`), `songCtx` (`prototype/aurora.js`). All 14
move to `views/` this section. `renderServiceCard` looked like a fifteenth
at first sweep, since `prototype-prism/song-pages.js` and
`prototype/presider-workspace.js` both reassign a same-named function; the
first review round traced `build.mjs` precisely and found that
reassignment is appended only to `song-app.js`'s own separate build output,
never spliced into `app.js`'s scope, so it was reverted (see Review below).

Fixed by generalizing the private-local-plus-setter pattern Section 3 used
for `render`/`renderBanners`/`pulse`: `app.js` keeps its own mutable `let`
for each of the 14, seeded from the real import before any gallery code
runs, so the monkey-patch lands on `app.js`'s own local instead of a
read-only ES import binding. Every other module that needs the live,
possibly-patched version receives it through a setter called from `init()`,
after the injected gallery code has already run. Four of the 14
(`renderSiteLock`, `renderManageServices`, `renderManagePlanning`,
`renderManageRequests`, `renderFeatures`, `renderManageData`, `songCtx`,
seven names, four collision sites) are both owned by and internally
dispatched-to from within their own module (`views/shell.js`'s `render()`,
`views/manage.js`'s `renderManage()`, `views/songs.js`'s `renderSongs()`),
so the real implementation keeps its name and the internal call site is
renamed to an `active`-prefixed local instead (five allowlist entries).
`renderManagePeople`, `renderUnlock` and `renderCreatePin` are reassigned
but never called by name anywhere in the app (confirmed by grep against the
frozen baseline), so they need only the `app.js`-local shadow, no rename,
no setter.

Fixed a real checker gap: `buildCurrentDeclarationIndex` treated every
`app.js`-local declaration as automatically eligible to be a baseline name's
"current home" regardless of export status, which collided with the new
`app.js`-local shadow `let`s. Fixed by excluding an `app.js` `let` whose name
the manifest assigns to a different, already-existing module. All 11
existing checker behavior tests still pass unmodified.
