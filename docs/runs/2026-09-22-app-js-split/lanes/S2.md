### The checker had three real bugs, found and fixed here

All three were latent in Section 1's `scripts/check-app-split.mjs` (which had only ever been exercised against an untouched tree with a single-file `app.js`), surfaced by actually moving real code for the first time:

1. **Multi-line imports were invisible.** `extractTopLevelImportedNames` matched only a single-line `import {...} from '...'`. `app.js`'s own import block (14 to 19 names per module, wrapped across several lines) was never seen, so `--gallery` reported all 14 re-imported gallery-scope names as missing even though they were correctly imported. Fixed: the import regexes now run globally over the whole source (their character classes already span newlines; only the matching strategy needed to change).
2. **A trailing section banner comment was attributed to the wrong declaration.** `extractDeclarations` defines a declaration's body as "start line through the next declaration's start line," which silently includes any banner comment sitting between two declarations assigned to *different* modules. Moving the earlier declaration alone (correctly, per the module map's line ranges) then failed as `edited`, because the baseline body it was compared against still carried the following module's banner text. Hit five times (once per module boundary in this section). Fixed: trailing blank lines and comments (including one wrapped across two lines) are trimmed off a body before comparison.
3. **A private local with a reused name looked like a duplicate.** Breaking the `state`/`departmentProfiles`/`departmentProfileAssignable` import cycle (below) meant `core/constants.js` and `core/planning.js` each declare their own non-exported local of the same name. The checker's duplicate check compared every top-level declaration by name regardless of export status, so it reported `duplicate: "state"` across three files. Fixed: only exported declarations (plus anything in `app.js` itself, which needs no export to be usable in its own scope) are candidates for "the current home of a baseline declaration."

Three new behavior tests cover these in `tests/check-app-split.test.mjs`, each verified to fail against the pre-fix checker and pass after.

### The plan's "acyclic by rule" claim for Section 2 was wrong

Discovered empirically, not by re-reading the plan more carefully: `memberLabel`/`feat`/`siteHash`/`sheetUrl` (assigned to `core/constants.js`) and `workloadStats`/`suggestSubs` (assigned to `core/planning.js`) all read `state`, and `suggestSubs` also calls `departmentProfiles`/`departmentProfileAssignable`, none of which move until Section 3. A plain `import {state} from '../app.js'` in those two leaf modules created a real ES module cycle back to the entry script. Because `app.js` also directly imports all five leaf modules, that cycle pulled the entire leaf-module graph into one strongly-connected component; in real Chromium (`node design-gallery/test.mjs`), `core/conflicts.js`'s top-level `const ALL_DUTIES_ORDER = CATEGORIES.reduce(...)` executed *before* `core/constants.js` had initialized `CATEGORIES`, throwing `ReferenceError: Cannot access 'CATEGORIES' before initialization`. This was reproduced directly in a headless browser (not inferred from spec-reading) before any fix was attempted, and every candidate fix was re-verified the same way rather than trusted from theory.

**Fix:** remove the back-import entirely. `core/constants.js` and `core/planning.js` each declare a private (non-exported) local of the same name and export a setter (`setConstantsStateRef`, `setPlanningRefs`); `app.js` calls each setter once, immediately after the real value it already owns is declared. This needed zero changes to the six affected declarations' own bodies (they still read plain `state`/`departmentProfiles`/`departmentProfileAssignable`, now resolving to the local placeholder), and the import graph is now a pure DAG. **Every later section that needs a not-yet-moved `app.js` symbol should use this same pattern**, not a real import back to the entry module.
