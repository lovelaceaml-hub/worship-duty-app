### The two most consequential findings this section

**1. Nine `let` bindings are reassigned, not just read, from outside `core/state.js`.** The plan's "Known cases" list (Interfaces, "Shared mutable state and setters") named only `sharedNameMap` and `setlistIndex`. In reality `state`, `fb`, `authReady`, `authUser`, `verifiedSession`, `authStatus`, `requestUnsub`, `departmentsLoaded`, `membersLoaded` are all reassigned from `app.js`'s `handleAct`/`handleChg`/`initFirebase`/`init` and, once moved, from `core/session.js`'s own functions. An ES import binding cannot be assigned to from outside its owning module (`TypeError: Assignment to constant variable.`, caught live at the first login attempt in Chromium). Fixed with `core/state.js` exporting nine setters; 16 call sites converted with 16 new allowlist entries.

**2. `app.js`'s Section 2 setters for `state`/`departmentProfiles`/`departmentProfileAssignable` were deliberately NOT "cleaned up" to real imports**, even though `core/state.js` and `core/departments.js` now exist to import from directly. Checked first: `core/constants.js` itself has no top-level statement depending on `state`, but `core/state.js` (the module a real import would pull `state` from) does: `ui.deptFilter` is an IIFE that calls `CATEGORIES.some(...)` at module top level, and `CATEGORIES` comes from `core/constants.js`. If `core/constants.js` imported `state` from `core/state.js` (which imports `CATEGORIES` back from `core/constants.js`), the two would form a 2-node import cycle with `core/constants.js` as the cycle's discovery root; per the ECMAScript module evaluation algorithm, a cycle's members execute in *reverse* discovery order, so `core/state.js` would run before `core/constants.js` and throw the exact `CATEGORIES` TDZ error Section 2 already found and fixed once, just relocated. Left both Section 2 setters exactly as built. **Rule for every remaining section:** before importing a not-yet-fully-wired binding back across module boundaries, check for a top-level (non-function) statement anywhere in the importing module's transitive dependency chain; if one exists, use the private-local-plus-setter pattern instead of a real import, regardless of how safe the specific new edge looks in isolation.

**3. A second, independently serious production bug: `render()` reference staleness.** `core/notify.js`, `core/sheet-sync.js` and `core/session.js` all need `render()`, which stays in `app.js` until Section 4. Their setter calls were first placed in `app.js`'s top-level preamble, right after the import block: this captures whichever `render` function exists *at that point in evaluation*, the plain pre-gallery version. `design-gallery/build.mjs`, the actual production build path (this app deploys through the design gallery, not a plain copy of `app.js`), injects `host-bridge.js` immediately before the final `init();` call, and that injection **monkey-patches `render`** into a version that also paints the active appearance (`design.afterRender()`; Prism/Navy/Aurora repainting). Calling the setters before that injection point would have permanently frozen these three modules onto the pre-patch function: every notify, sheet-sync and session event (new-duty alerts, sheet pulls, login, PIN change, logout) would silently skip appearance-specific repainting for every real user on Prism, Navy or Aurora, in production, after release. Caught only because `design-gallery/test.mjs`'s first-visit appearance dialog never auto-opened after login; a manual `window.WorshipDesign.open(true)` call confirmed the underlying permission checks (`isAccessible()`) were correct, isolating the fault to `render()` never reaching `design.afterRender()`. Fixed by moving those three setter calls into `init()`'s own body (its first three statements), which runs after all top-level code, including the host-bridge.js injection, has already executed. `findService`/`renderBanners`/`pulse` are never monkey-patched (confirmed by reading `host-bridge.js`'s own redefinition list), so those stayed safe wherever they were called.

### The `main`-as-baseline command drifts once a section's substitution has landed

Discovered doing a routine post-merge sanity check (not part of this section's own required verification, done out of caution): `node scripts/check-app-split.mjs main --manifest ... --gallery`, run against `main` after Section 2 merged, produced 3 false failures, because `main`'s `app.js` already contains Section 1's and Section 2's allowlisted substitutions baked into its actual text, and re-applying those same allowlist entries against it double-applies them. `main` was never wrong for a section's own pre-merge, in-branch verification (it is genuinely that branch's pre-section state); it only breaks as a generic post-hoc baseline reference. Fixed generally: `readBaselineSource` now accepts a bare 40-hex git blob hash (detected via `git cat-file -t`, read directly via `git show <blob>`, no path suffix needed), which is content-addressed and therefore immune to drift. `tests/check-app-split.test.mjs`'s self-test switched from `'main'` to `manifest.baseline.blob` (already recorded there since Section 1). A new regression test proves a commit-ish baseline whose own content already has a substitution baked in produces a failure rather than a silent double-application. **Every verification command from Section 4 onward should pass the manifest's own `baseline.blob`, not the literal string `main`.**

### Two more checker bugs, found building real code for the first time at this scale

1. The trailing-comment trim (Section 2's review fix) found a block comment's opener via `line.includes('/*')`, which false-positives on ordinary prose containing that two-character sequence, e.g. `"firebase.json's /ics/** rewrite)"`. A real `downloadICS()` doc comment was left half-trimmed, producing an unterminated-comment syntax error in `core/calendar.js`. Fixed: the opener must start the line (`^\s*\/\*`), matching every real comment style in this codebase.
2. `buildCurrentDeclarationIndex` compared every top-level declaration by name regardless of export status, so the new private-local setter pattern's same-named module-private locals (`state` inside `core/constants.js` and `core/planning.js`) registered as `duplicate: "state"`. Fixed: only exported declarations (plus anything directly in `app.js`, which needs no export to be usable in its own scope) are eligible to be "the current home" of a baseline declaration.

Both are covered by new regression tests; `tests/check-app-split.test.mjs` grew from 10 tests to 11.
