## Result

**Increment 1 of 4 (Member screens) is complete and committed** as `681f2d6` on `claude/compact-runtime`: "Section 4 increment 1: Member screens (My duties, Availability, Reminders)".

Built, following the real Section 2 contract:

- **`#duties`** ("My next duty" / Upcoming duties, the member start screen): featured next-duty card, duties grouped by day/service, a "Request change" inline form per duty (pending state shown, submits through the existing `persistRequest`/Firestore-request domain code, not a new callable), and a "Your requests" history list. New pure builder `buildDutiesInfo(host, mem)` in `shared/screens.js`; new host methods `hostMyDuties`, `hostMyRequests`, `hostSubmitChangeRequest` in `app.js`, reusing the existing `dutiesFor()`, `findPendingRequest()`, `persistRequest()`, `actionableDepartmentForDuty()`.
- **`#availability`**: one card per department the member belongs to (a member can be in more than one), recurring service-time toggles, date exceptions with add/remove, Save/Discard per card. This **reuses the existing, already-wired `updateMemberAvailability` Cloud Function** (via the pre-existing `saveOwnDepartmentAvailability()`/`departmentRuntime` draft system that already powers the leader-facing Manage screens) rather than the not-yet-built `saveMemberAvailability` the work order named — functionally equivalent to plan section 2's "member availability defaults to all their departments, with selected-department exceptions." Wrapped in `shared/save-state.js`'s `createSave()` for Unsaved/Saving/Saved/Failed, with a generic `wd-save-retry` handler in `shared/shell.js` that finds the right department/member via the nearest `[data-dept][data-uid]` ancestor (reusable by later increments' save bars, not just this one).
- **`#reminders`**: notification on/off, calendar (ICS) subscribe/copy-link, recent alerts with clear — all pre-existing app.js behavior (`notifyOn()`, `registerPush()`, `subscribeICS()`, `copyICSLink()`), exposed read-only plus actions through the host.
- Screen registry: `shared/screens.js` `SCREEN_IDS`/`screenForRoute()` now route `#duties`/`#availability`/`#reminders` to their own screens instead of falling through to `legacy`. This is the actual removal of that slice of the `.wd-legacy` bridge — `hostLegacyMy()`/`renderMy()` in `app.js` are now unreachable via routing (left in place as dead code rather than deleted, to avoid an unrelated blind removal in a production file under time pressure; a follow-up can delete them once Manage/Songs replace the rest of the bridge).
- All three screens are implemented once in `layouts/_common.js`'s shared `createLayout()` factory (not per-appearance), so `layouts/original.js`, `prism.js`, `navy.js`, `aurora.js` all get them automatically with no forked markup — only shared `shared/components.js` primitives are used. `layouts/index.js`'s `REQUIRED_SCREENS` now includes `duties`/`availability`/`reminders`, so `verifyLayouts()` fails loudly if a future edit drops one from any layout.

Changed files: `app.js`, `shared/screens.js`, `shared/shell.js`, `layouts/_common.js`, `layouts/index.js`.
