## 2026-09-17: Section 6 corrections

Two bounded client-side corrections, made directly in this worktree on `claude/compact-integration`, per Anthony's request. No deploy, no `release.mjs`, no push, no production access, no new test suites, `functions/` and `firestore.rules` untouched.

### Fix 1: stale-save witnesses on every client write

Before this fix, no client call sent `expectedRevision`/`expectedUpdatedAt`/`expectedMemberName`, so `assertFresh` on the server was always a no-op (per S3-SERVER-INTERFACE.md section 3.1, a missing `expectedRevision` is a no-op) and no write could ever be rejected as stale, even though the server-side check has existed since Section 3. Every client call to a version-aware callable now sends the witness it last displayed, and stores the revision the server returns for the next save:

- `assignDepartmentDuty` / `overrideDepartmentAssignment` / `unassignDepartmentDuty` (`app.js`, `departmentAssignmentPayload`/`unassignDepartmentDutyForService`, new helper `departmentAssignmentWitness`): `expectedRevision` from `svc.assignmentRevisions[duty]` (missing reads as 0) and `expectedMemberName` from `svc.assignments[duty]` (`''` when empty), read from the same `svc` object the leader/administrator screen already has in hand (not a fresh re-fetch). New helper `applyAssignmentRevision` writes the server's returned `revision` back onto `svc.assignmentRevisions[duty]` after a successful save, so a second assignment in the same session builds a fresh witness. These three primitives are reached today only from the still-live `.wd-legacy` Manage bridge (direct assign/unassign controls); the compact `#manage/attention` screen calls `resolveDutyAttention` instead (below), never these three directly.
- `resolveDutyAttention` (`app.js`, `hostResolveAttention`): same witness shape, computed from `findService(item.serviceId)` at the moment of the resolve action, `item` coming from the same `hostAttentionItems()` computation that built what is displayed in Needs attention -- not a separately fetched fresher value. On success, `applyAssignmentRevision` updates the local slot revision. On failure, `failed-precondition` with `details.reason === 'conflict'` is still handled as the pre-existing advisory (shows the warning, lets the caller retry with `acknowledgeConflict: true`, now with a clarifying comment); every other rejection (including the new `aborted` stale case) now uses the server's own message via `departmentErrorMessage()` instead of the unrelated PIN-login `safeAuthMessage()`, which was the wrong message function already in place there and would have shown "That member name and PIN did not match." for a stale resolve now that staleness is actually reachable.
- `updateDepartmentProfile` / `updateMemberAvailability` (`app.js`, `departmentPatch`/`saveDepartmentProfile`, both callers share this code): the witness is captured once, in `departmentPatch`, the moment a draft is first created for a department/member (the first edit, i.e. when the editor opens for that record) from `profile.revision`/`profile.updatedAt` -- not re-read from the draft at save time. `saveDepartmentProfile` adds `expectedRevision`/`expectedUpdatedAt` into the `patch` object sent to the callable (per S3-SERVER-INTERFACE.md section 3.2, these live inside the command allowlist, stripped before `normalizeProfilePatch`). `replaceDepartmentProfile` already deletes the draft and replaces the roster entry with the server's returned (now current-revision) profile on success, so the next edit captures a fresh witness automatically.
- `saveSongService` (`app.js`, `hostConfirmSongsRun`/`hostPresiderServices`): new `presiderSongWitness` cache, populated the first time a service appears in the My-service list (`ensurePresiderSongWitness`, called from `hostPresiderServices`) from the live `setlistIndex[serviceId]` at that moment, not re-read at confirm time. A service with no setlist document yet gets `null` (no witness sent) -- the brand-new-setlist case the work order called out. Updated with the server's returned `revision`/`setlist.updatedAt` after a successful confirm.
- `correctSongHistory` (`app.js`, `loadSongHistory`/`hostRemoveHistorySong`): `expectedRevision`/`expectedUpdatedAt` are now captured directly on each history entry when the History list loads (`loadSongHistory`'s `snap.docs.map(...)`, which previously dropped these fields entirely), sent on every Remove, and updated from the response afterward. The error banner on rejection now shows the server's own message instead of `safeAuthMessage()` (same wrong-function issue as `resolveDutyAttention`).
- `saveMemberAvailability`: confirmed, again, that no client call uses this callable name anywhere in this worktree (`grep -rn "saveMemberAvailability" app.js shared layouts` returns nothing but the doc comments) -- Section 4's lane record already disclosed that the Availability screen reuses `updateMemberAvailability` instead. Nothing to wire for this specific callable name; the equivalent live path (`updateMemberAvailability`) is the one fixed above.

`shared/save-state.js`: `isStale()` was already correctly treating `aborted` and `failed-precondition` (prefix-stripped, `functions/aborted` -> `aborted`) as Stale, and `createSave`'s rejection handler already kept the draft on a Failed/Stale rejection -- this was already correct per the S2 ruling and needed no change. Added a `staleMessage()` helper so the Stale message can surface who changed it when the rejection's `details` includes `updatedBy` (profile/song saves) or `assignedBy`/`memberName` (assignment slot), per the S3 `details` shapes in section 3.1's table; falls back to the server's plain message when no such field is present. Confirmed `error.details` survives the round trip unmodified: the Firebase callable error wrapper (`fb.callable(name)(payload)` in `authCall`, and the raw Firebase JS SDK underneath it) already exposes `.code`, `.message`, and `.details` on a `functions.https.HttpsError` rejection without any wrapping in this codebase, and `app.js` already relied on `error.details` at the pre-existing conflict-advisory site, so no normalization was needed beyond the prefix-stripping `save-state.js` already had.

### Fix 2: hide `#manage/exceptions`

Checked `shared/nav.js`'s `secondaryFor()` first: the built compact secondary tabs for `#manage` (Schedule, Needs attention, Members, Settings-for-admin) never actually included an Exceptions tab in the real implementation -- that link only ever existed in the design prototype (`docs/design/prototype/compact-phone/app.js`), not in this shipped code. So the placeholder was reachable only by a direct/typed `#manage/exceptions` URL, which `shared/screens.js`'s `screenForRoute()` mapped to a real `manageExceptions` screen (an honest empty-state placeholder, `layouts/_common.js`'s `screenManageExceptions`).

Removed it at the route-registry level rather than special-casing it: `shared/state.js`'s `ROUTES` list no longer includes `'#manage/exceptions'`, so `isKnownRoute()` returns false for it, and `shared/shell.js`'s existing `resolveRoute()` already sends any unknown route to `#unavailable` (the same path a typo or unauthorized destination takes) -- this is the "existing unavailable screen like any unknown or unauthorized route" the work order asked for, with no new logic. Also removed, for registry consistency (`verifyLayouts()` requires every layout to implement exactly the same screen set): the `manageExceptions` entry from `shared/screens.js`'s `SCREEN_IDS` and `screenForRoute()`, the now-dead `buildManageExceptionsInfo()` export, the dispatch line in `shared/shell.js`, the `manageExceptions` entry from `layouts/index.js`'s `REQUIRED_SCREENS`, and the `screenManageExceptions()` function plus its registry entry in `layouts/_common.js` (the single shared factory all four layouts use, so this is one removal, not four). No layout-specific file needed touching. Noting per the work order: hidden pending a defined exception data model -- `S3-MEMBERSHIP-INTERFACE.md` still defines only a not-found search result, never a persisted "administrator exception" record, so nothing was invented to replace what was removed.
