### Fix 1: stale-save witnesses on every client write

Before this fix, no client call sent `expectedRevision`/`expectedUpdatedAt`/`expectedMemberName`, so `assertFresh` on the server was always a no-op (per S3-SERVER-INTERFACE.md section 3.1, a missing `expectedRevision` is a no-op) and no write could ever be rejected as stale, even though the server-side check has existed since Section 3. Every client call to a version-aware callable now sends the witness it last displayed, and stores the revision the server returns for the next save:

- `assignDepartmentDuty` / `overrideDepartmentAssignment` / `unassignDepartmentDuty` (`app.js`, `departmentAssignmentPayload`/`unassignDepartmentDutyForService`, new helper `departmentAssignmentWitness`): `expectedRevision` from `svc.assignmentRevisions[duty]` (missing reads as 0) and `expectedMemberName` from `svc.assignments[duty]` (`''` when empty), read from the same `svc` object the leader/administrator screen already has in hand (not a fresh re-fetch). New helper `applyAssignmentRevision` writes the server's returned `revision` back onto `svc.assignmentRevisions[duty]` after a successful save, so a second assignment in the same session builds a fresh witness. These three primitives are reached today only from the still-live `.wd-legacy` Manage bridge (direct assign/unassign controls); the compact `#manage/attention` screen calls `resolveDutyAttention` instead (below), never these three directly.
- `resolveDutyAttention` (`app.js`, `hostResolveAttention`): same witness shape, computed from `findService(item.serviceId)` at the moment of the resolve action, `item` coming from the same `hostAttentionItems()` computation that built what is displayed in Needs attention -- not a separately fetched fresher value. On success, `applyAssignmentRevision` updates the local slot revision. On failure, `failed-precondition` with `details.reason === 'conflict'` is still handled as the pre-existing advisory (shows the warning, lets the caller retry with `acknowledgeConflict: true`, now with a clarifying comment); every other rejection (including the new `aborted` stale case) now uses the server's own message via `departmentErrorMessage()` instead of the unrelated PIN-login `safeAuthMessage()`, which was the wrong message function already in place there and would have shown "That member name and PIN did not match." for a stale resolve now that staleness is actually reachable.
- `updateDepartmentProfile` / `updateMemberAvailability` (`app.js`, `departmentPatch`/`saveDepartmentProfile`, both callers share this code): the witness is captured once, in `departmentPatch`, the moment a draft is first created for a department/member (the first edit, i.e. when the editor opens for that record) from `profile.revision`/`profile.updatedAt` -- not re-read from the draft at save time. `saveDepartmentProfile` adds `expectedRevision`/`expectedUpdatedAt` into the `patch` object sent to the callable (per S3-SERVER-INTERFACE.md section 3.2, these live inside the command allowlist, stripped before `normalizeProfilePatch`). `replaceDepartmentProfile` already deletes the draft and replaces the roster entry with the server's returned (now current-revision) profile on success, so the next edit captures a fresh witness automatically.

Updated with the server's returned `revision`/`setlist.updatedAt` after a successful confirm.
- `correctSongHistory` (`app.js`, `loadSongHistory`/`hostRemoveHistorySong`): `expectedRevision`/`expectedUpdatedAt` are now captured directly on each history entry when the History list loads (`loadSongHistory`'s `snap.docs.map(...)`, which previously dropped these fields entirely), sent on every Remove, and updated from the response afterward. Each finding was confirmed in the code before anything was changed. All seven were real.

### Finding 1 (blocking): profile witnesses sent inside `patch`

Confirmed. `saveDepartmentProfile` put `expectedRevision`/`expectedUpdatedAt` into the `patch` object. On the server, `patchFromRequest` reads the witness from the top level (`data.expectedRevision`) and, when `data.patch` is present, hands `data.patch` straight to `authz.normalizeProfilePatch`, whose `safeKeys` check rejects any key outside `PROFILE_MUTABLE_FIELDS`. Every profile and availability save would have failed with `invalid-argument`.

Corrected: the witness now sits at the top level of the callable payload beside `departmentId`/`memberUid`/`patch`, built by a new `departmentSaveWitness()` helper.

A second, unreported defect of the same root cause was found and fixed with it. The witness had been stored *inside the draft object*, and a draft is a patch of real profile fields: `saveOwnDepartmentAvailability`'s guard (`Object.keys(draft).some(field => field !== 'availability')`) therefore rejected every compact Availability save with "Only availability changes may be saved from My Duties", and `departmentDraftProfile` merged the witness keys into the displayed profile. Witnesses now live in `departmentRuntime.witnesses`, keyed the same way as the drafts and cleared with them in `replaceDepartmentProfile` and `clearDepartmentRuntime`.

### Finding 2 (blocking): availability saved through the wrong callable

Confirmed. Availability saved through `updateMemberAvailability`, which writes the profile but never runs the Needs-replacement fan-out, so a member could become unavailable for a service they are still assigned to and no leader would ever be told.

Corrected: a new `saveDepartmentAvailability()` sends `saveMemberAvailability` with `{ memberUid, departments: [{ departmentId, availability, expectedRevision, expectedUpdatedAt }] }`, the full availability object for the department as ruling section 1.2 requires. `saveDepartmentProfile` routes to it whenever the patch is availability-only, so a leader editing a member's availability uses the same callable as the member. Every returned profile is stored through `replaceDepartmentProfile`, which is what carries each department's new revision into the next save's witness. A new `announceReplacementMarks()` reports `replacements.marked` in plain words: the member stays assigned, and the duty is now flagged for a leader to find a replacement, named by duty and service date.

### Finding 3 (blocking): `functions/compact-membership.js` never wired

Confirmed: the module was never required or exported, so all four handlers were unreachable.

Server: `functions/index.js` now requires the module, instantiates `createCompactMembershipHandlers({ db, now })` (the factory's third argument, `randomBytes`, defaults to Node crypto exactly as the interface ruling asks), and exports `searchDepartmentCandidates`, `createDepartmentInvitation`, `revokeDepartmentInvitation` and `acceptDepartmentInvitation` through `exposeDepartmentCallable`.

Checked, as the work order asked, whether that wrapper fits accept. It does. `exposeDepartmentCallable` only establishes a verified, active, current-role, no-forced-PIN actor through `callableActor`; it applies no department authority of its own. Search, create and revoke call `assertManagement` inside the handler, while `acceptDepartmentInvitation` deliberately does not, which is exactly the "any signed-in member" rule the membership ruling states. The `AUTH_ERROR_CODES` set already carries `already-exists` and `failed-precondition`, so accept's outcome codes reach the client instead of being masked as `internal`.

`firestore.rules`: direct client access to `departmentInvitations` was already denied by the deny-by-default `match /{document=**}` at the end of the file, so nothing was open. Added an explicit `match /departmentInvitations/{invitationId} { allow read, write: if false; }` anyway, which grants nothing new (Firestore matches are additive, and `if false` can never widen access) and states the boundary so a later edit cannot open it by accident.

Client: `hostCreateInvite` now builds a real link, `location.origin + location.pathname + '#invite/' + encodeURIComponent(token)`, and the Members screen shows the link with Share (`navigator.share` when available, falling back to Copy) and Copy link, plus a plain confirmation line. The token is never logged, never put in a query string, and never written anywhere.

New `#invite/<token>` accept route: added to `shared/state.js`'s `ROUTES`, to `SCREEN_IDS` and `screenForRoute` in `shared/screens.js` (with a new `buildInviteInfo` builder), to the dispatch in `shared/shell.js`, to `REQUIRED_SCREENS` in `layouts/index.js`, and implemented once as `screenInvite` in the shared `layouts/_common.js` factory, so all four appearances get it and `verifyLayouts()` passes. `startShell` stores an invite route as the pending destination so it survives the sign-in screen and is consumed once after `ready`. A route with no token (`#invite/`) is not a known route and resolves to `#unavailable` like any other unknown destination. Outcomes are shown in plain words: joined, already a member (nothing changed), expired or withdrawn, already used, and a generic retry for anything else. Accepting refreshes the member's own department profiles, because the new roster entry changes what the account can see.

### Finding 4 (blocking): presider song witness went stale

Confirmed. `ensurePresiderSongWitness` captured once (`if (!(serviceId in presiderSongWitness))`) and never refreshed. Confirm has no compact draft of its own: it reads the live `setlistIndex` entry, and the presider picks songs in the legacy `song-app.js` picker, which bumps the setlist's `updatedAt`. The presider's own picks would therefore make their own Confirm fail as a conflict, every time.

Corrected: the witness is re-captured whenever the displayed setlist's `revision` or `updatedAt` moves, and is held fixed only while that service's own confirm is in flight (the compact side has no song draft, so an in-flight save is the only "unsaved" state there is). `hostConfirmSongsRun` derives the witness from the very setlist object the songs it is sending were read from, so what is sent always matches what the presider is looking at.

### Finding 5 (follow-up): removing the last recorded song

Confirmed: `correctSongHistory` requires a non-empty `songs` array, so Remove on the last song could only ever produce an error.

Corrected in the shared layout factory: when a recorded service has one song left, Remove is replaced by "Last song, cannot be removed". The server rule is unchanged.

### Finding 6 (follow-up): protecting the two server-owned schedule fields

Decision: fixed entirely on the client, and `firestore.rules` was **not** loosened.

Checked the allowlists first. `adminScheduleUpdate` and every sibling (`changesWorshipAssignments`, `changesUsherSistersAssignments`, `changesUsherBrothersAssignments`, `changesLobbyAssignments`, `changesTranslationAssignments`, `changesMediaAssignments` and the rest) are `hasOnly` lists that already omit `needsReplacement` and `assignmentRevisions`. That is correct and must stay: a client that could name either key could forge or clear a replacement marker, or reset a stale-save counter. Adding them would be exactly the wrong fix.

The real risk was the other direction. Every browser write to `schedule/{id}` is a whole-document `setDoc`, so a document assembled from an older copy (this device's offline copy, a spreadsheet import, a locally built service object) would silently delete a marker the server added since, and because a deletion is an affected key, the rules would then reject the whole save as a side effect.

Corrected: `app.js` now keeps the latest `needsReplacement` and `assignmentRevisions` the schedule listener saw, per service id, and `serviceWriteBody()` carries those values through unchanged on every full-document write (`persistService` and the batched `persistAll`). Because the written values are identical to the stored ones, neither key appears in the rules diff at all, so a race can neither delete a marker nor trip the allowlist. If the server has no such field, the key is dropped from the payload rather than invented.

### Finding 7 (follow-up): unescaped department name

Confirmed at `layouts/_common.js`: the roster heading interpolated `info.department` directly. Now wrapped in `c.esc`.
