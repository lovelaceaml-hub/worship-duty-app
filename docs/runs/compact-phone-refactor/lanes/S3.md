# S3: Server workflows

## Work order

Implement the remaining Section 3 server interfaces the Section 2 handoff flagged as still needing a ruling: authorized multi-department availability, atomic Needs-attention (request/assignment) resolution, version-aware saves for assignments/profiles/songs, and idempotent automatic song history with authorized correction. The membership interface (search/invite/accept) was already ruled and out of scope here. Own `functions/` and `firestore.rules` only. No deploys, no production writes, no migrations.

## Fable ruling

Before writing code, dispatched a read-only Fable 5.1 architect ruling covering the four remaining areas, grounded in the actual existing code (`department-handlers.js`, `department-auth.js`, `index.js`, `song-app.js`'s `confirmedAt`/`updatedAt` convention, the existing `requests`/`departmentAssignments`/`setlists`/`songStats` collections). Saved at `docs/runs/compact-phone-refactor/decisions/S3-SERVER-INTERFACE.md`. Fable wrote no code.

The ruling's exact field name for the schedule-change collection (`serviceId`) did not match the real existing field (`svcId`, confirmed by reading `app.js`'s request-creation code). Implemented against the real field names; this is execution-level fidelity to already-settled existing schema, not an architecture disagreement, so it was not escalated back to the controller.

## Verification

No new test suites (plan directive). Ran the existing suite unchanged: `node --test test/*.test.js` — 56/56 passing (functions/test/, including department-seed, member-auth, sheet-lib, sheet-protection, public-schedule, leader-notifications, index text-assertions). `node --check` on every changed/added file.

Wrote a throwaway smoke script (`/private/tmp/.../scratchpad/smoke-section3.js` + a hand-written in-memory Firestore/transaction fake that enforces the real "no second write to the same document in one transaction" rule) exercising, against realistic seeded data (`Usher Sisters` department, `Usher Door` duty, a leader token shaped like production custom claims):
- `assignDepartmentDuty`/`unassignDepartmentDuty`: revision starts at 1, bumps on each write, survives unassign; a stale `expectedRevision`/`expectedMemberName` witness is rejected with `aborted`.
- `resolveDutyAttention`: assigns a replacement atomically; a same-service conflict is rejected with `failed-precondition` and `details.reason: 'conflict'`; an acknowledged conflict proceeds and records `conflictOk`; opening a duty with no replacement clears the slot without creating an administrator help request; a pending request is declined (no slot change) and separately approved-with-replacement (links `assignmentId`).
- `saveMemberAvailability`: marking a department unavailable marks `needsReplacement` on the affected future service without touching the existing assignment; becoming available again clears the marker; the marker fan-out found the affected `departmentAssignments` record via the two-equality query.
- `saveSongService`: creates a setlist, then confirms it (`confirmedAt >= updatedAt`); a second direct save after the automatic recorder marks it `sung` is rejected with `failed-precondition` ("Use a correction").
- `recordSongHistory`: skips a confirmed list before its service's three-hour window has passed; records it once the window passes (`historySource: 'automatic'`, `songStats` `timesSung` incremented); a second run is a no-op (idempotent, per-service history-entry check).
- `correctSongHistory`: drops one song and adds another on an already-recorded list; the dropped song's stats doc is deleted (history now empty) and the added song gets one `source: 'corrected'` entry; `historySource` flips to `'corrected'`.

All checks passed. This caught and fixed one real bug during development: an early draft issued more than one `transaction.set`/`update` call against the same schedule document within a single transaction (Firestore rejects this), for both `saveMemberAvailability`'s multi-duty Needs-replacement fan-out and `resolveDutyAttention`'s combined assignments/assignmentRevisions/needsReplacement-clear/conflictOk write; both now accumulate into one merged object per document before the single write.

No Firestore emulator run (Java is not installed on this Mac; confirmed via `java -version` failure) and no live/authenticated walkthrough — this section ships no client-observable behavior (Section 4 wires the compact UI to these callables). Nothing deployed; no production writes; no migrations.

- `saveMemberAvailability`'s per-department availability write is a full replacement of that department's `availability` object (matching the existing single-profile `updateMemberAvailability` convention), not a partial merge.
- The rules-allowlist additions (`revision` on `departmentProfileKeysSafe`/`assignmentKeysSafe`) were checked by reading the rule functions and their call sites, not by running the emulator (no Java on this Mac). `assignmentKeysSafe`'s two call sites are already unreachable (`departmentAssignments` create/update/delete are all `if false`), so that half of the change is inert but harmless; `departmentProfileKeysSafe` gates a live read path and was the one that mattered.

## Section 4 handoff

Callables ready to call from the compact client, all through `exposeDepartmentCallable`, all returning `{ ok: true, revision, ... }` on success and rejecting a stale write with code `aborted` plus a `details` payload (which `shared/save-state.js` per the Section 2 ruling should read for the Stale explanation):

- `saveMemberAvailability({ memberUid, departments: [{ departmentId, availability, expectedRevision?, expectedUpdatedAt? }] })` → `{ revision, departments: [{ departmentId, revision, profile }], replacements: { marked, cleared } }`.
- `resolveDutyAttention({ departmentId, serviceId, duty, requestId?, decision?, replacementMemberUid?, acknowledgeConflict?, expectedRevision?, expectedMemberName? })` → `{ revision, serviceId, duty, memberName, assignment, requestId, requestStatus }`. A conflict without `acknowledgeConflict: true` rejects `failed-precondition` with `details: { reason: 'conflict', duties }` — show the advisory and retry with `acknowledgeConflict: true`.
- `saveSongService({ serviceId, songs, glorySong, thanksSong, notes, confirm, expectedRevision?, expectedUpdatedAt? })` → `{ revision, serviceId, setlist }`. Rejects `failed-precondition` once the service is recorded (`status: 'sung'`) — the UI must switch to `correctSongHistory` at that point.
- `correctSongHistory({ serviceId, songs, glorySong?, thanksSong?, notes?, expectedRevision?, expectedUpdatedAt? })` → `{ revision, serviceId, setlist, changedSongs }`.
- `assignDepartmentDuty`/`overrideDepartmentAssignment`/`unassignDepartmentDuty`/`updateDepartmentProfile`/`updateMemberAvailability` unchanged in shape, now additionally accept `expectedRevision`/`expectedMemberName` (assignment calls) or `expectedRevision`/`expectedUpdatedAt` (profile calls) and always return `revision`.

Needs-attention derivation (for the information builder behind `#manage/attention`) is a client-side computation over existing data, not a new collection: `requests` where `status === 'pending'` and the requester still holds `assignments[duty]` (existing `requestIsActionable`); `schedule.needsReplacement[duty]` where the marker is still live; `schedule.assignments[duty]` empty for a future service in a managed department; and the existing `activeConflicts`/`conflictOk` convention for conflicts. See `docs/runs/compact-phone-refactor/decisions/S3-SERVER-INTERFACE.md` section 2.1 for the exact predicate table.
